第一阶段: Ping 通网络 ✅ 已完成

第一阶段跑了 3 个任务 + 修了 5 个 Bug, 最终 FPGA 能回复 ARP 和 ICMP。

任务 1: 搭建 iverilog 仿真环境

进展和结果: 用 iverilog 搭了一个完整的仿真环境。FPGA 的 RTL 代码用了很多 Xilinx 原语(IDELAYE2、IDDR、ODDR、MMCM、xpm_memory), iverilog 不认识这些, 手写了行为级 Stub 来替换。仿真时 BFM 读 firmware.hex 模拟 JTAG 写指令 RAM, 然后 testbench 注入 ARP Request 帧到 RGMII 接口, 观察整个链路是否走通。仿真验证通过了: gmii_rx_dv 拉高 → mac_rx_sop/eop 脉冲 → cpu_rd_empty 拉低, 链路全通。固件也顺便编译过了, 2634 bytes。 仿真覆盖了哪些: 

tb.v (注入 ARP Request 帧到 GMII)
  → xilinx_stubs.v   (用行为级代码替换 Xilinx 原语)
  → vendor_stubs.v   (MMCM 时钟直通, 跳过 PLL)
  → lcpu_bfm.v       (读 firmware.hex, 模拟 JTAG 写固件到指令 RAM)
  → RTL 全部真实模块  (rgmii_gmii_bridge → gmii2mac → mac_top → cpu_channel → pktfifo → picorv32)

仿真的链路: 帧从 RGMII 进来 → IDDR 采样转 GMII → MAC 定界 → FIFO 缓存 → PicoRV32 读包 → C 固件处理 → 写回复包到 TX FIFO → MAC 发送 → ODDR 转 RGMII 输出。

仿真覆盖的是逻辑正确性, 不覆盖 PHY 配置、物理时序、UART、真实 JTAG。这些只能上板调。

遇到和解决的问题:

RGMII 驱动时序写错了。testbench 在 rgmii_rxc 同一边沿驱动 rgmii_rxd 数据, IDDR 采样时新旧值还没稳定, gmii_rx_dv 永远不拉高。改成 opposite-edge: negedge 设低 4 位, posedge 设高 4 位, 给 IDDR 留出一个半周期的稳定窗口。

iverilog 仿真非常慢, 因为 RTL 模块里内嵌了 testbench(gmii2mac、crc、fifo 等), 仿真时这些内部 testbench 也在跑, 占掉了大部分仿真时间。

仿真文件清单: 

sim/
├── Makefile           # 一键编译+运行
├── tb.v               # 主 testbench, 注入 ARP Request 帧
├── tb_fast.v          # 精简版 testbench (跳过内部自检, 仿真更快)
├── lcpu_bfm.v         # BFM, 从 firmware.hex 读固件模拟 JTAG 写入
├── xilinx_stubs.v     # Xilinx 原语行为级替换
└── vendor_stubs.v     # MMCM 时钟 Stub


使用 tb_fast.v 时需将 Makefile 中 `SIM_SRCS` 的 `tb.v` 改为 `tb_fast.v`。



运行:

cd sim

python3 ../c_build/tcl2hex.py ../tcl/InstructRAM.tcl firmware.hex   # 固件转 hex

make clean && make      # 编译

make run                # 跑仿真, 生成 tb.vcd

make wave               # GTKWave 看波形

任务 2: 上板验证 + 烧录

进展和结果: 上板烧录后 LED 流水灯在跑, 证明 CPU 活者。PHY 的 Link LED 亮, ping 时 Activity LED 闪, 说明 PHY 收到了 PC 发的包。但 FPGA 不回复——折腾了很久才发现问题根本不在代码。 遇到和解决的问题:

最大的坑: 固件根本没烧进 FPGA。v3 的 build.tcl 只生成了纯 RTL 的 bitstream, PicoRV32 的指令 RAM 初始值全是 0, CPU 起来读到全零指令直接崩溃。v4 能跑是因为用了 updatemem 把 firmware.bin 嵌入 BRAM INIT。复制 v4 的 update_and_program.sh, 加一步 updatemem 把 bank*.mem 写入 bitstream, 烧录后 LED 自检正常——问题解决。

FPGA 软核和 STM32 不一样。STM32 烧录时自动把程序写进 Flash, FPGA 软核的 bitstream 里 BRAM 初始值是什么 CPU 起来就跑什么。这步理解错了, 浪费了很多时间。

任务 3: Ping 验证

进展和结果: 修好烧录问题后, ping 169.254.1.1 一次成功。第一个包 1059ms(PC 先发 ARP 学 MAC), 后续稳定 2ms。全链路验证通过。

第一阶段修掉的 5 个 Bug

  • 栈指针未初始化: PicoRV32 上电 sp=0, 第一个函数调用写 0xFFFFFFFC 跑飞。rename_entry 加 la sp, _stack_top 解决。
  • .bss 段未清零: 绕过 picolibc CRT, 静态变量值不确定。加 bss 清零循环。
  • 仿真延时过长: 5M 次 nop 循环在 iverilog 里跑 3 秒。加 SIM_FAST 宏跳过。
  • BFM 复位卡死: timer 变量在 delay 和 OP_DONE 间复用。拆成两个独立计数器。
  • RGMII 采样竞争: 同边沿驱动。改 opposite-edge。

第二阶段从零写 TCP 协议栈。按照自底向上的顺序: 先定义数据结构和解析, 再做校验和, 最后实现握手状态机。

任务 7: 新建 tcp.c/tcp.h — 头文件和数据定义

7a. 头文件和结构体

进展和结果: 创建了 tcp.h(声明) 和 tcp.c(实现)。tcp.h 里定义了: 7 个 TCP 状态常量、6 个 Flag 宏、MAX_TCP_CONN=4、tcp_conn_t 结构体(8 个字段: state/remote_ip/remote_port/local_seq/remote_seq/remote_ack/retry_count/timeout)、extern 全局变量声明、API 函数原型。tcp.c 实现了连接表管理(tcp_init/find_conn/alloc_slot/free_slot)和 RX FIFO 读辅助函数(tcp_rd16/tcp_rd32)。 遇到的问题: tcp.h include 路径写错了——#include "inc/lcpu_general.h"。tcp.h 自己在 inc/ 目录下, 再加 inc 前缀找成了 inc/inc/lcpu_general.h, 编译挂了。 学到的:

.h 和 .c 的 include 路径规则不一样。编译时 Makefile 通过 -I 指定了 inc 目录, .c 文件里写 #include "inc/xxx.h" 能找到。但 .h 文件自己就在 inc 目录里, 互相 include 时直接写文件名不加路径, 加 inc/ 多了一层反而找不到。一个简单规则: inc 里的头文件互相 include 不加前缀, .c 文件 include inc/ 下的头文件才写 #include "inc/xxx.h"。

extern 只是声明不占内存。在 .h 里写 extern uint32 src_ip; 是告诉编译器"这个变量存在", 但必须在某一个 .c 里写 uint32 src_ip; 才能真正分配内存。忘了在 .c 里定义, 链接时就会报 undefined reference。

typedef 不分配变量。typedef struct { int x; } Point; 只是给类型起了名字, 并没有创建变量。初学者容易写成 Point;(啥也没做)或忘记写 Point p; 然后用 p 访问。

static 函数不写进 .h。加了 static 的函数只在当前 .c 文件内可见, .h 里不需要声明它, 其他 .c 文件也看不到。这是一种封装——把不需要暴露给外部的内部函数藏起来。

RX FIFO 和 TX FIFO 是不同的硬件。LCPU_RD_SET_ADDR 操作的是 RX 读指针, LCPU_WR_BYTE 操作的是 TX 写指针。已经从 RX 读了数据写到 TX 了, 就别想再从 TX 读回来了——硬件没这条路。

宏重复定义编译有 warning。TCP_SYN_RETRY_TICKS 和 HTTP_PORT 在 lcpu_general.h 和 tcp.h 各有一份, 删掉 tcp.h 的重复定义, 统一用 lcpu_general.h 的值。

注释风格统一。去掉了 /* ==== 大块分隔线和任务编号注释, 改用单行 // 标注。[cite: N] 粘贴残留全部清掉。代码逻辑一行没改, 编译 0 warning 0 error。

7b. TCP 报文解析

进展和结果: 实现了 tcp_parse_header: LCPU_RD_SET_ADDR 跳到帧偏移 34(TCP 头起点), 用 tcp_rd16/tcp_rd32 逐字段读 SrcPort(2B)、DstPort(2B)、SEQ(4B)、ACK_Num(4B)、DataOffset(高4bit→头长度)、Flags(1B)、Window(2B)。TCP payload 长度 = ip_total_len - ip_header_len - 实际的 TCP 头长度。解析完自动调 tcp_find_conn 用 src_ip + tcp_src_port 查连接表, 返回匹配的连接槽索引。 遇到的问题: 这一版没有编译错误, 但之前写的校验和函数 tcp_checksum_out 有个根本性错误——想从 RX FIFO 读取刚写到 TX FIFO 的数据。两个 FIFO 是独立硬件, 互相读不到。这个错误留到任务 8 重做。 学到的:

数组越界在嵌入式环境特别危险。for (i = 0; i < MAX_TCP_CONN; i++) 没问题, 但写成 i <= MAX_TCP_CONN 就多访问了一个元素。嵌入式没有 MMU 保护, 越界不会 segfault, 会静默破坏隔壁变量的值, 极难排查。

C 语言函数用 -1 表示"找不到"。tcp_find_conn 返回 -1 时, 调用方必须检查, 不检查就 conn_table[-1] 访问, 行为未定义。

7c. TCP 报文发送通路

进展和结果: 实现了 tcp_wr16/tcp_wr32——向 TX FIFO 写大端 16/32 位值。TCP 发包的顺序是: eth_proc 先预写 MAC 头(源 MAC + 交换 MAC) → ip_header_update 预写 IP 头(交换 IP + 重算 checksum) → TCP 层写 TCP 头字段(SrcPort→DstPort→SEQ→ACK→DataOffset+Flags→Window→Checksum→Urgent) → LCPU_WR_PUSH_PACKET 推送。握手包 54 字节 < 64, 补零到最小帧。 学到的:

网络字节序是大端——高位字节在前, 低位字节在后。tcp_wr16(addr, 0x1234) 写出来 addr 地址是 0x12, addr+1 是 0x34。如果误用 x86 的小端思维, 写成了 0x34 在前, Wireshark 看到的端口号就是错的, PC 内核直接丢弃。

以太网最小帧 64 字节。TCP 握手只有 54 字节不够, 末尾必须补零。忘了补零就是 runt frame, 很多交换机/PHY 会直接扔掉。

发包顺序非常重要——必须先写 MAC 头再写 IP 头再写 TCP 头。反过来就不行了, 因为 eth_proc 和 ip_header_update 操作的是 RX FIFO 的读指针, 而 TCP 发包函数操作的是 TX FIFO 的写指针——它们之间不共享地址空间, 但硬件协议栈要求数据在 TX FIFO 里按 MAC→IP→TCP 的顺序排列。

任务 8: TCP 校验和 + IP 分派

8a. 校验和计算

进展和结果: 重写了校验和函数, 新的 tcp_calc_checksum 完全基于函数参数传入的值——不读任何 FIFO。9 个参数: src_ip, dst_ip, src_port, dst_port, seq, ack, flags, window, payload_len。先算伪首部 6 次 cks_sum_cal, 再算 TCP 头 10 次 cks_sum_cal, 取反返回。发包函数在外面先调 tcp_calc_checksum 算出值, 再写 TCP 头时把校验和回填进去。 遇到的问题: 上一版 tcp_checksum_out 的错误根源——想从 RX FIFO 的地址空间去读 TX FIFO 刚写入的数据。这两个 FIFO 硬件上就是独立的, 互访做不到。只能在写 TX 之前用纯寄存器参数算好校验和。 学到的:

校验和的伪首部不实际发送。12 字节伪首部(SrcIP + DstIP + Zero + Proto + TCP_Length)只参与 Checksum 计算, 一定不要写进 TX FIFO。很多初学者把它当作 TCP 头的一部分也写了进去, 导致 TCP 头多 12 字节。

校验和最后一步必须取反。return ~sum 不是 return sum。忘了取反, Wireshark 会显示 TCP Checksum Incorrect 的红色标记, PC 内核静默丢掉这个包——表面上"发出去没回复", 其实包发出去了但被对方丢了。

8b. main.c 增加 TCP 分派

进展和结果: main.c 已加入 #include "inc/tcp.h"、tcp_init() 调用、主循环 TCP_PROC 分支。固件从 2634 → 4508 bytes (1127 words, 22.0%)。TCP 函数已链接进固件。 学到的:

连接 TCP 分派后固件涨了 1874 字节——链接器把 tcp.o 里被引用的符号(tcp_init、tcp_proc、tcp_parse_header、tcp_calc_checksum、tcp_send_syn_ack、tcp_send_rst、tcp_handle_listen、tcp_handle_syn_received 及它们依赖的 tcp_wr16/wr32/rd16/rd32、cks_sum_cal 等)全部拉进了最终 ELF。

仿真验证: tb_fast.v 从 ARP 帧去掉了多余的 8 字节前导码(GMII 层不需要), 帧注入延迟到 RTL 内部 testbench 全部跑完后(50ms), 避免内部自检模块抢读 RX FIFO。主固件已包含 TCP 代码, 仿真验证 ARP+ICMP 链路是否仍然正常。

任务 9: SYN 处理 — 回复 SYN+ACK

进展和结果: 实现了三个核心函数: tcp_proc(主入口, 解析→分发), tcp_handle_listen(收到 SYN→分槽→回 SYN+ACK), tcp_handle_syn_received(收到 ACK→验证→进 ESTABLISHED)。整个握手流程: PC 发 SYN(DstPort=80) → FPGA tcp_parse_header 解析 → tcp_handle_listen 分配槽位、记录对方 IP 和端口和 SEQ、生成自己的 ISN=0x10000000 → tcp_send_syn_ack 构造回复包(Flags=SYN|ACK=0x12, ACK_Num=对方SEQ+1, Window=1460, Checksum 预计算) → LCPU_WR_PUSH_PACKET 发送。PC 收到后发 ACK → FPGA tcp_handle_syn_received 验证通过 → 连接进入 ESTABLISHED。 学到的:

SYN 也消耗一个序号——这是 TCP 初学者最容易写错的点。握手第二步的 ACK_Num 是对方的 SEQ+1, 不是 SEQ。因为 SYN 标志消耗了对方的序号, 下一个期望的字节序号就是 SEQ+1。忘了 +1, PC 的 TCP 栈会发现 ACK 号不对, 连接建立失败。

开发阶段固定 ISN 是可以的。正式 TCP 实现用随机 ISN(防攻击), 但调试时固定值(如 0x10000000)的好处是 Wireshark 里一眼就能认出来是自己发的包。

switch/case 的 default 不要空着。tcp_proc 的 switch 有 default: break, 但如果状态机意外进入未处理状态, 包被静默丢弃。至少该加个 LED 闪烁或调试输出提示异常。

网络调试助手发 SYN 前 PC 会先发 ARP。别奇怪 Wireshark 里先看到 ARP 再看到 TCP——这是正常的, PC 必须知道 FPGA 的 MAC 地址才能发 IP 包。如果之前 ping 过, ARP 表有缓存, 就跳过这一步。
